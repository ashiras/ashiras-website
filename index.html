02 / GENERATIVE AI ARCHITECTURE

AIを「設計問題」として解く

生成AIの出力は本質的に確率的である。最新論文を追うのではなく、「状態空間における軌道のズレ」として定式化し、大規模開発の現場で回る Trajectory Design に落とし込む。中を賢くするな。外を設計しろ。

確率的AIの軌道制御

コンテキスト長 N の増大で初期制約の注意確率 PN は死滅する。続く自己回帰はズレを蓄積する。プロンプトを磨くのではなく、止める点・固定する点・照合する点・引き戻す点をアーキテクチャが担う。

Trajectory DesignControl State

Rollback ≠ Recovery

履歴を巻き戻すことと、正常な制御状態（Control State）へ復帰することは別問題である。局所整合ではなく Artifact の外部固定を優先し、人間ゲートをハブにした復帰条件を設計対象とする。

03 / PARADIGM SHIFT

現象を式に書き、現場に落とす。

意味の Drift、長文の Crowding、Agent の発散、Harness、Plan / Rewind も、先に観測されるふるまいとして扱う。それを設計変数へ写す。ずれは自己回帰の累積として定義する。

Dt+1 = Dt + gt(Dt) + ηt − δt

履歴の巻き戻しと Control State への復帰は別操作とする。Artifact は系の外へ固定し、人間ゲートを復帰条件のハブにする。論文の語彙を機能名へ写すのではなく、現場が操作できる制約へ落とすことが重要である。

04 / FRONT-END ENGINEERING

フレームワークを追うな。コアを置け。

UIパーツが持つのは、見た目と振る舞いである。React や Angular が持つのは、ページを組み立て、状態を持ち、更新を配る層である。層が違うものを、同じ文法の上に置くな。ボタンを React コンポーネントとして書く必要はない。マルチフレームワークの現場では、それが再利用できるかどうかそのものになる。コアは DOM と純関数に置き、枠ごとの書き味だけ薄いラッパーに残す。表舞台に出ることはないが、すでに多くの上場企業の裏側で、この UI Core が静かにシステムを支え続けている。

Web ComponentsPure JS

UIパーツとフレームワークは、層が違う

パーツを枠の寿命に縛った瞬間、Angular の管理画面と React の新規アプリで、同じボタンを二度書くことになる。コアを純関数と DOM 標準に置けば、素の HTML からも同じ振る舞いが出る。CVA も状態転写も皮で足りる。寄せるのは呼び出し側だけだ。マルチフレームワークを採用するほど、依存の向きはこう逆になる。

Color ConceptPalette Engineering

配色を、感覚ではなく計算にする

デザイナーが画面の上で置いている色の配置を、工学側で出す。メインカラーから補色のアクセント、同系色のベース、背景輝度に対する文字色を計算する。現場で使っているものを公開した。

補色で視線をボタンと通知へ送る。同系色で白背景より階層を出す。輝度から白／黒を自動判定し、無彩色でも同化させない。

05 / COMPANY

会社概要

一つの思想、二つの基盤

生成AI領域では軌道を置く。フロントエンド領域ではコアを置く。配色は計算する。外を設計し、現場は分ける。

自由度を内側に足しても、軌道は安定しない。モデルを大きくしても、フレームワークを厚くしても、ずれは内側で増える。安定するのは固定点である。生成列なら止める点と復帰条件。UIなら見た目と振る舞いのコア。配色なら補色・同系色・輝度の関係。先にそれを外へ置く。内側は、その上で交換してよい。
